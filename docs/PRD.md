# PDF 문서 변환 서비스 PRD

## 1. 문서 정보

- 문서명: PDF 문서 변환 서비스 제품 요구사항 문서
- 작성일: 2026-06-05
- 제품 목적: PDF 파일을 수정 가능한 문서 형식으로 변환하는 웹 서비스 제공
- 1차 핵심 목표: PDF를 DOCX, HWP 등 사용자가 직접 수정할 수 있는 문서로 변환
- 기본 기술 방향: Next.js 프론트엔드, Spring Boot 백엔드, Gradle 빌드, PostgreSQL 데이터베이스

## 2. 배경

PDF는 배포와 보관에는 적합하지만, 문서 내용을 다시 편집하거나 재사용하기 어렵다. 특히 스캔본 PDF, 관공서 문서, 계약서, 견적서, 보고서처럼 한국어 문서와 표가 포함된 파일은 일반 변환 도구에서 품질이 낮거나 후처리 비용이 크다.

본 서비스는 단순 파일 포맷 변환이 아니라, 문서의 텍스트, 표, 이미지, 제목, 문단 구조를 최대한 복원해 사용자가 실제로 편집할 수 있는 문서로 만드는 것을 목표로 한다.

## 3. 제품 비전

PDF를 Word 또는 HWP처럼 다시 편집 가능한 문서로 바꿔주는 한국어 중심 문서 변환 서비스.

## 4. 목표

### 4.1 핵심 목표

- PDF 파일을 DOCX 형식으로 변환한다.
- 스캔 PDF를 OCR 처리해 편집 가능한 텍스트 문서로 변환한다.
- 한국어 문서의 문단, 표, 제목 구조를 최대한 보존한다.
- 변환 결과를 사용자가 다운로드할 수 있게 한다.

### 4.2 확장 목표

- PDF를 HWP 형식 또는 HWP 편집에 적합한 대체 형식으로 제공한다.
- 표가 포함된 PDF를 XLSX 또는 CSV로 추출한다.
- 원본 PDF와 변환 결과를 비교할 수 있는 미리보기 화면을 제공한다.
- 개인정보 자동 감지 및 마스킹 기능을 제공한다.
- 일괄 변환과 API를 통해 기업 고객 사용성을 확장한다.

## 5. 대상 사용자

### 5.1 개인 사용자

- PDF 문서를 Word처럼 수정하고 싶은 사용자
- 스캔 문서의 텍스트를 추출하고 싶은 사용자
- 과제, 보고서, 신청서, 계약서 파일을 다시 편집해야 하는 사용자

### 5.2 업무 사용자

- 계약서, 견적서, 제안서, 공문을 편집 가능한 문서로 복원해야 하는 실무자
- PDF 표 데이터를 Excel로 추출해야 하는 회계, 세무, 영업, 운영 담당자
- 반복적인 문서 변환 작업을 처리해야 하는 기업 사용자

### 5.3 관리자 및 기업 고객

- 팀 단위 변환 이력과 권한을 관리해야 하는 조직
- 사내 시스템에서 문서 변환 API를 사용하려는 개발팀
- 보안, 개인정보, 파일 보관 정책이 필요한 기업

## 6. 핵심 사용자 시나리오

### 6.1 일반 PDF를 DOCX로 변환

1. 사용자가 PDF 파일을 업로드한다.
2. 변환 형식으로 DOCX를 선택한다.
3. 서비스가 문서 구조를 분석한다.
4. 사용자는 변환된 DOCX 파일을 다운로드한다.

### 6.2 스캔 PDF를 편집 가능한 문서로 변환

1. 사용자가 스캔본 PDF를 업로드한다.
2. 서비스가 이미지 기반 PDF 여부를 감지한다.
3. OCR 처리를 수행한다.
4. OCR 신뢰도가 낮은 영역을 표시한다.
5. 사용자는 DOCX 또는 TXT 파일로 다운로드한다.

### 6.3 PDF 표 데이터를 Excel로 추출

1. 사용자가 표가 포함된 PDF를 업로드한다.
2. 서비스가 페이지별 표 영역을 감지한다.
3. 사용자가 추출할 표 또는 페이지 범위를 선택한다.
4. 서비스가 XLSX 또는 CSV 파일을 생성한다.

### 6.4 변환 전 페이지 정리

1. 사용자가 PDF를 업로드한다.
2. 페이지 회전, 삭제, 순서 변경, 범위 선택을 수행한다.
3. 정리된 페이지 기준으로 문서를 변환한다.

## 7. 기능 요구사항

### 7.1 파일 업로드

- 사용자는 PDF 파일을 업로드할 수 있어야 한다.
- 드래그 앤 드롭과 파일 선택 업로드를 지원해야 한다.
- MVP 기준 최대 파일 크기는 50MB로 제한한다.
- 지원하지 않는 파일 또는 손상된 파일은 명확한 오류 메시지를 제공해야 한다.
- 업로드 API는 Spring Boot 백엔드에서 제공한다.
- 업로드된 파일의 메타데이터와 처리 상태는 PostgreSQL에 저장한다.

### 7.2 PDF 분석

- 텍스트 기반 PDF와 이미지 기반 PDF를 구분해야 한다.
- 페이지 수, 파일 크기, 암호화 여부를 감지해야 한다.
- 표, 이미지, 텍스트 블록, 제목 후보 영역을 식별해야 한다.
- MVP에서는 Java 기반 PDF 분석 라이브러리를 우선 검증한다.

### 7.3 PDF to DOCX 변환

- PDF의 텍스트를 DOCX 문서의 편집 가능한 텍스트로 변환해야 한다.
- 제목, 문단, 목록, 표 구조를 최대한 보존해야 한다.
- 이미지와 도장, 서명 등 시각 요소는 문서 내 이미지로 유지해야 한다.
- 원본 PDF가 1장인 경우, 변환 결과도 가능한 한 1장 안에서 해결해야 한다.
- 1장 유지 여부는 Microsoft Word와 LibreOffice Writer 렌더링 결과를 기준으로 검증한다.
- 1장 PDF의 편집 우선 변환에서는 페이지 수 증가를 유발하는 불필요한 제목, 원본 전체 미리보기 이미지를 기본 삽입하지 않는다.
- 사용자는 레이아웃 유지 모드와 편집 우선 모드 중 선택할 수 있어야 한다.
- MVP에서는 Spring Boot 내부 변환 모듈 또는 같은 저장소의 Java worker 모듈을 통해 변환을 수행한다.
- 변환 품질 한계가 명확한 경우 Python 또는 외부 변환 워커로 분리할 수 있도록 API와 작업 모델을 독립적으로 설계한다.

### 7.4 OCR 변환

- 이미지 기반 PDF에 대해 OCR을 수행해야 한다.
- MVP에서는 한국어와 영어를 우선 지원한다.
- OCR 결과는 DOCX 또는 TXT로 다운로드할 수 있어야 한다.
- OCR 신뢰도가 낮은 영역은 추후 미리보기 화면에서 표시할 수 있어야 한다.
- OCR은 Java 연동 가능한 로컬 OCR 엔진을 우선 검토하고, 품질 또는 운영 비용 기준에 따라 외부 OCR API를 별도 검토한다.

### 7.5 HWP 변환

- 1차 확장 기능으로 HWP 다운로드를 제공한다.
- 직접 HWP 생성이 어렵거나 라이선스 제약이 있는 경우, HWP에서 열어 편집하기 쉬운 DOCX 또는 HTML 기반 대체 경로를 제공한다.
- 한국 관공서 문서, 공문, 신청서 양식의 구조 보존을 우선 고려한다.
- 2026-06-06 검증 기준 LibreOffice는 DOCX to HWP 쓰기 export filter를 제공하지 않아 직접 `.hwp` 생성에 실패했다.
- HWP 직접 생성 전까지는 한글 워드프로세서에서 열어 편집 가능한 DOCX를 우선 제공한다.

### 7.6 표 추출

- PDF 내 표를 감지하고 XLSX 또는 CSV로 추출할 수 있어야 한다.
- 표가 여러 페이지에 걸쳐 있는 경우 페이지별 시트 또는 하나의 병합 시트로 저장할 수 있어야 한다.
- 숫자, 날짜, 금액 형식은 가능한 범위에서 유지해야 한다.

### 7.7 변환 결과 다운로드

- 변환 완료 후 사용자는 결과 파일을 다운로드할 수 있어야 한다.
- 결과 파일명은 원본 파일명과 변환 형식을 기반으로 생성한다.
- 변환 실패 시 부분 결과가 있는 경우 다운로드 가능 여부를 안내한다.
- 다운로드 요청은 작업 상태가 완료된 파일에 대해서만 허용한다.

### 7.8 작업 상태 관리

- 모든 변환 요청은 작업 단위로 생성되어야 한다.
- 작업 상태는 대기, 처리 중, 완료, 실패로 구분한다.
- 작업 상태와 오류 메시지는 PostgreSQL에 저장한다.
- 사용자는 프론트엔드에서 작업 상태를 조회할 수 있어야 한다.
- 서버 재시작 후에도 완료, 실패, 대기 상태를 확인할 수 있어야 한다.

### 7.9 파일 관리 및 보안

- 업로드 파일과 변환 결과는 기본적으로 일정 시간 후 자동 삭제해야 한다.
- MVP 기준 보관 시간은 24시간 이하로 설정한다.
- 민감 문서 처리를 고려해 전송 구간 암호화를 적용해야 한다.
- 기업 플랜에서는 즉시 삭제, 저장 금지, 감사 로그 옵션을 제공할 수 있어야 한다.
- 파일 경로, 크기, 만료 시간, 삭제 상태는 PostgreSQL에 저장한다.

### 7.10 개인정보 마스킹

- 확장 기능으로 주민등록번호, 전화번호, 이메일, 계좌번호 패턴을 감지한다.
- 사용자는 변환 전 또는 변환 후 마스킹 여부를 선택할 수 있다.
- 마스킹 결과는 원본과 별도 파일로 제공한다.

### 7.11 일괄 변환

- 여러 PDF 파일을 한 번에 업로드할 수 있어야 한다.
- 파일별 변환 상태와 실패 사유를 표시해야 한다.
- 완료된 파일은 개별 다운로드 또는 ZIP 다운로드를 지원한다.

### 7.12 API 제공

- 기업 고객은 API를 통해 파일 업로드, 변환 요청, 상태 조회, 결과 다운로드를 수행할 수 있어야 한다.
- API 키 기반 인증을 제공한다.
- 요금제별 요청량, 파일 크기, 동시 처리 제한을 적용한다.

## 8. 비기능 요구사항

### 8.1 성능

- 10페이지 이하 일반 PDF의 DOCX 변환은 목표 60초 이내로 완료한다.
- 10페이지 이하 스캔 PDF의 OCR 변환은 목표 180초 이내로 완료한다.
- 변환 작업은 비동기 큐 기반으로 처리해 브라우저 타임아웃을 방지한다.

### 8.2 안정성

- 변환 작업 실패 시 사용자에게 실패 사유와 재시도 방법을 안내한다.
- 변환 작업 상태는 대기, 처리 중, 완료, 실패로 구분한다.
- 서버 재시작 시 진행 중인 작업의 상태를 복구할 수 있어야 한다.
- PostgreSQL에 저장된 작업 상태를 기준으로 재시도와 장애 복구 흐름을 설계한다.

### 8.3 보안

- 업로드와 다운로드는 HTTPS를 사용한다.
- 파일 접근 URL은 예측 불가능한 토큰을 사용하고 만료 시간을 둔다.
- 업로드 파일의 확장자와 MIME 타입을 검증한다.
- 악성 파일 탐지 또는 격리 처리를 고려한다.
- Spring Security 기반 인증과 인가 확장을 고려한다.

### 8.4 개인정보 및 컴플라이언스

- 기본 정책으로 업로드 파일과 결과 파일의 자동 삭제 시간을 명시한다.
- 사용자가 직접 파일을 삭제할 수 있는 기능을 제공한다.
- 기업 고객용으로 파일 미보관 옵션과 처리 로그를 제공한다.

### 8.5 사용성

- 사용자는 업로드 후 3단계 이내에 변환을 시작할 수 있어야 한다.
- 변환 대기 중 진행 상태를 확인할 수 있어야 한다.
- 모바일에서도 업로드, 상태 확인, 다운로드가 가능해야 한다.

## 11. 주요 리스크

- PDF 구조가 파일마다 달라 변환 품질 편차가 클 수 있다.
- OCR 품질이 원본 스캔 상태에 크게 의존한다.
- HWP 직접 생성은 라이선스, 포맷 호환성, 구현 난이도 이슈가 있다.
- 대용량 파일과 동시 변환 처리 비용이 높을 수 있다.
- 민감 문서 업로드에 대한 사용자 신뢰 확보가 필요하다.
- Java 기반 변환 라이브러리만으로 DOCX 편집 품질을 충분히 확보하지 못할 수 있다.
- 변환 엔진을 외부 worker로 분리할 경우 운영 복잡도가 증가할 수 있다.

## 12. 오픈 이슈

- HWP 직접 변환은 별도 도구 또는 라이브러리 검토가 필요하다. 현재는 DOCX 기반 대체 경로를 먼저 제공한다.
- OCR 엔진을 클라우드 API로 사용할지 자체 호스팅 엔진으로 사용할지 결정해야 한다.
- 변환 품질 평가 기준과 테스트 문서 세트를 정의해야 한다.
- 무료 사용자의 파일 크기, 페이지 수, 일일 변환 횟수 제한을 정해야 한다.
- 파일 보관 시간과 삭제 정책을 서비스 약관에 반영해야 한다.
- Spring Boot 내부 비동기 처리, Spring Batch, PostgreSQL polling, 메시지 큐 중 MVP 작업 처리 방식을 결정해야 한다.
- Java 기반 변환 엔진으로 충분한지, Python 변환 워커를 별도 도입해야 하는지 PoC 결과로 결정해야 한다.
